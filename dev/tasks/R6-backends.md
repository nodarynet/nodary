# R6 — Backends

**Deliverable:** backend descriptors beyond vLLM — SGLang, llama.cpp.
**Proves:** pluggability is real, not theoretical.
· [00 §8](../specs/00-overview.md#8-milestones)

Deliverable level. Break these into tasks when R6 starts.

Stopping after R6 is a complete outcome. R1–R5 deliver the whole stated goal with
no frontend; R6 is what makes "adding a backend is a TOML file, not a code change"
true rather than claimed.

Backends are data, not code: a descriptor is inert and schema-validated, where a
plugin directory of arbitrary Python would reopen the hole the release signature
closes. · [04 §1](../specs/04-backends.md#1-why-descriptors-rather-than-plugins)

- [x] **R6-02** Embed the built-in descriptors — vLLM, SGLang, llama.cpp, TensorRT-LLM; `/etc/nodary/backends/` holds only operator-added ones · [01 §12](../specs/01-install.md#12-filesystem-layout)
  - **withdrawn 2026-09-15: TensorRT-LLM is no longer shipped** — descriptor, pin and manifest entry removed ([R6b §5](../plans/R6b-the-silicon-matrix.md)). It is lowest priority against the silicon matrix and can come back on customer demand; nothing was orphaned, because it declared no `prepare` (below) and no Go code named it outside comments. The three that remain are vLLM, SGLang and llama.cpp
  - *done:* all four are embedded. **TensorRT-LLM needed no `[backend.prepare]` after all, and the reason it was thought to is worth keeping.** 0.x served an engine directory — `convert_checkpoint.py`, `trtllm-build`, then serve the output — which is exactly what §4's stage → prepare → serve exists for. 1.x's serving path compiles in-process from a HuggingFace checkpoint: the quick-start is `trtllm-serve "TinyLlama/TinyLlama-1.1B-Chat-v1.0"` and nothing is built first. Read from the 1.2.0 sources the pinned digest is a build of, not from memory
  - **the consequence is not the missing table, it is `tensor_parallel`.** It is a *runtime* flag here (`--tp_size`, parsed by trtllm-serve), so a descriptor written to the old shape would have consumed it into a build and dropped it from the argv of the server that wants it — a deployment that starts, serves, and quietly runs on one GPU. Pinned by a test, because nothing else would notice
  - `--host` defaults to `localhost` in `tensorrt_llm/commands/serve.py`, so the descriptor sets it for llama.cpp's reason: otherwise the server binds a loopback that is not the one the published port maps to, and every request is refused by a deployment reporting healthy
  - `quantization` is declared **empty** rather than listing formats. TensorRT-LLM serves quantized weights by being pointed at a quantized checkpoint — the quick-start's own `nvidia/Qwen3-8B-FP8` — and there is no quantization parameter for the list to be the closed vocabulary *of*. A list here would read as enforced and would not be
  - the image is pinned per platform from `nvcr.io`'s manifest list for `1.2.1`, resolved through the registry's anonymous token, the way every other backend here is pinned
  - *unverified on hardware:* nothing here has served a token. The argv and the pinning are covered by tests; a real checkpoint on a real GPU is not
  - two and not one, deliberately: a single descriptor cannot demonstrate the translation is data-driven, because one vocabulary is indistinguishable from a hard-coded one
  - **llama.cpp is the third, and the one that shows the format carries more than a vocabulary.** vLLM and SGLang differ only in spelling; this one differs in shape — a single GGUF rather than a HuggingFace cache, an option with no canonical equivalent, and `cpu_offload = true`, a server that runs where there is no VRAM
  - **`[backend.extra]` is a second table, not more rows in `args`.** A name in `args` is one nodary *translates* — `max_context` reaches vLLM as `--max-model-len` and SGLang as `--context-length`, and a document means the same thing against either. A name in `extra` is one it merely *passes*, so moving a deployment to another backend is expected to refuse rather than quietly mean something else. It is still named, unlike `extra_args`: `gpu_layers: 33` is spelled by the descriptor, so a typo is refused instead of reaching the container. A name in both tables is refused — whichever lookup ran first would otherwise become the answer
  - **the `single-file` layout produced no usable model path, and nothing would have found it but running the layout through.** `unitFor` special-cased `hf-cache` and otherwise used `mount_path` bare, so llama.cpp would have been told `-m /models` — a directory — and failed at start with a message about the file format, a long way from the cause. Only the manifest knows the weights' name, so `SingleFileName` reads it: exactly one entry, or an error saying what it found
  - it runs **even under `--no-verify`**, because that flag exists to skip re-reading hundreds of gigabytes of weights and the manifest is a few lines of text. Otherwise `agent plan` could never render a llama.cpp argv at all
  - a **sharded GGUF is refused, not guessed at**. llama.cpp takes the first shard, and inventing that convention here would serve the wrong weights in silence on the day the naming differs. The refusal names the manifest
  - a weights file whose name holds whitespace is refused for the reason `extra_args` already is: the name lands in `NODARY_ARGS`, which the unit expands unquoted so systemd splits it
  - **`model register` hardcoded `hf-cache` in two places** — the directory it digests and the artifact kind it stamps — so `--backend llama-cpp` looked for a HuggingFace cache a GGUF is not in, and then wrote a kind `config.Apply` refuses. Both now come from the descriptor, which [`internal/config/apply.go`](../../internal/config/apply.go) already called the authority: *"each descriptor declares one `weights_layout`"*. The "no weights at" message names what to place for the layout, because telling somebody with a GGUF to place `config.json and the tensor files` sends them looking for files their model does not have
  - *unverified on hardware:* nothing here has served a token. The argv, the layout, the manifest resolution and the registration path are covered by tests; a real GGUF on a real GPU is not
- [x] **R6-04b** A descriptor declares environment, including **host-conditional** environment
  - `[backend.env]` applies everywhere, `[backend.env_wsl2]` only on a WSL2 node. "vLLM will not start on WSL2 without `VLLM_WSL2_ENABLE_PIN_MEMORY`" is a fact about **vLLM**, not about nodary or about one operator's deployment, so it belongs in the descriptor — which is [04 §1](../specs/04-backends.md#1-why-descriptors-rather-than-plugins)'s argument for descriptors rather than plugins
  - detection, not a toggle: a fleet with both WSL2 and native nodes works without anybody remembering which is which, and a native host is never handed a variable that means nothing there
  - **the deployment wins** over both. Without that, the fallback for a host the descriptor's default does not fix would be unreachable — and that is exactly when an operator is setting one
  - one condition, not a condition engine. A second condition can generalise it; inventing the general form for a single case would be a mechanism nobody has exercised
- [x] **R6-04a** A deployment carries container **environment**, not only arguments
  - a backend is configured by both and only the first was expressible. The case that proved it: on WSL2 — a platform [01 §8](../specs/01-install.md#8-platform-support) supports — vLLM refuses to start with `RuntimeError: UVA is not available`, and both published fixes (`VLLM_WSL2_ENABLE_PIN_MEMORY=1`, `VLLM_USE_V2_MODEL_RUNNER=0`) are environment variables with no command-line form. **No deployment could be made to run at all**
  - it lands **now** rather than later because `config.Deployment` is a revision's hash preimage, and [mvp §2](../plans/mvp.md#2-the-rule-that-decides-what-gets-built) makes adding a field to that preimage the one change that invalidates every chain a customer already holds
  - rendered sorted, and whitespace is **refused rather than escaped** — the unit expands it unquoted so systemd splits it, exactly as `extra_args` does and for the same reason
- [x] **R6-03** Canonical parameter translation through `[backend.args]`, with `extra_args` appended verbatim and explicitly uninterpreted · [04 §3](../specs/04-backends.md#3-normalize-the-few-pass-through-the-rest)
  - a parameter the descriptor does not name is **dropped and the deployment refused**, never guessed. Inventing `--max-context=` for a backend that spells it differently produces a container that fails at start for a reason nobody can trace back to the translation
  - the argv order is fixed. It goes into a unit's environment file, and a set that reordered between reconciles would rewrite the file and restart a serving model for no reason
  - JSON numbers render as integers where they are integers: `--tensor-parallel-size=2.000000` is a container that will not start
- [x] **R6-04** Capability validation at enable time, not crash time · [04 §7](../specs/04-backends.md#7-validation)
  - *done:* every row of the validation table is rejected with its named message — including `tensor_parallel` on llama.cpp pointing at what it has instead, an unsupported quantization listing what is supported, and parallelism exceeding assigned GPUs. The test *is* the table
  - **"enable time" had to mean the applier, not the node.** The agent already refuses a deployment whose parameters the descriptor cannot render (R6-03), and that was nearly enough to call this done — but it happens on a GPU host up to a minute later, so what an operator sees is a change that was accepted and then did not happen. [`checkCapabilities`](../../internal/config/apply.go) runs before the insert, so the refusal is in the preview in front of the person who wrote it and the row never reaches the database
  - **`[backend.capabilities] quantization` had no parameter to be the vocabulary of.** It was parsed by R6-01 and read by nothing. The spec's example was `dtype: awq`, but `--dtype` and `--quantization` are different flags on every backend that has both, so validating a dtype against a quantization list would have rejected `bfloat16`. A canonical `quantization` is named in the vLLM and SGLang descriptors instead, and [04 §7](../specs/04-backends.md#7-validation)'s row now says so
  - **the alternative in a refusal comes out of the descriptor.** Hard-coding "use `--tensor-split`" would put a fact about llama.cpp in nodary's code — the thing [04 §1](../specs/04-backends.md#1-why-descriptors-rather-than-plugins) says descriptors exist to prevent — and it would go stale silently the first time a backend changed its options. `[backend.extra]` already means "options this backend names", so that is what is read; llama.cpp's descriptor gained `tensor_split` there, which also makes it reachable with a typo-checked spelling rather than only through raw `extra_args`
  - **a degree of 1 is not parallelism**, and refusing it would make a document that spells out its defaults unportable between backends for no difference in what runs
  - wrapped in `config.ErrInvalid` rather than returned as `backend.ErrUnsupported`, which is in neither front end's error table: an unwrapped one reaches an API client as a 500 with the message withheld, and R2-44 found that shape five times
- [x] **R6-05** `weights_layout` checked against the model's artifact kind before anything is staged or started · [04 §7](../specs/04-backends.md#7-validation)
  - *done:* [`checkArtifact`](../../internal/config/apply.go) refuses at apply time, so a GGUF registered against vLLM never reaches a node — the backend is the authority, since each descriptor declares exactly one `weights_layout`
  - it was built alongside R6-02's `single-file` work and had **no test of its own**, which is how a check quietly stops being one. It is row three of R6-04's table now, driven with the other three
  - an unknown backend is left alone, deliberately: R6 owns which backends exist, and refusing here would make the applier a second place that decides
- [x] **R6-06** The `prepare` phase: stage → prepare → serve · [04 §4](../specs/04-backends.md#4-the-prepare-phase)
  - *done:* a backend that declares `[backend.prepare]` builds before it serves; `gpu_arch_specific` artifacts are not treated as portable; a failed or timed-out prepare marks the deployment `failed` with the build log tail, leaves weights staged, and caches nothing
  - **it runs on the node, which is the opposite of a derived image (R6-09).** A derive is a container built once for a fleet; this is an engine compiled against the card it will serve from, and the control plane has no such card
  - the same shape as staging ([`stageunit.go`](../../internal/agent/stageunit.go)): a transient unit rather than work inside the agent process, a request file rather than flags, a progress file rather than a mutex. A six-hour compile has no business inside the long-lived root daemon holding this node's mTLS key, and it has to survive an agent restart without starting over
  - **the artifact is content-addressed**, on the weights digest, the backend, the builder image, the exact argv and — only when the descriptor says the output is not portable — the GPU model names. A cache keyed on the deployment id would serve an A100 engine on an L40S after a card swap: not an error anything reports, just wrong numbers
  - **the marker says a build finished, not the directory.** A builder killed at the timeout leaves a directory of partial output, so the child builds into `<dir>.building`, renames on success, and writes the marker *last* — the other order leaves a marker for a directory that is not there, which serves a broken engine
  - **a parameter the build consumes is not one the server dropped.** A build that substitutes a canonical parameter leaves the server without it, and `unitFor` would otherwise refuse the only document that could configure the build. `Prepare.Consumes()` is derived from the command's `{tp}` rather than declared, so a descriptor cannot claim to consume what it never substitutes
  - **the motivating example was wrong, and R6-02 found it.** This row said `tensor_parallel` is baked into a TensorRT-LLM engine at build time so `trtllm-serve` may not take it as a flag at all. That is 0.x, which served an engine directory; in 1.x — the release R6-02 pins — `trtllm-serve` parses `--tp_size` itself and compiles in-process, so TensorRT-LLM declares no prepare and consumes nothing. The mechanism is still right for a backend whose build genuinely swallows a parameter; it has no user today, and the code comment says so rather than asserting something false about the one backend it named
  - the unit is rendered while the build runs and `reconcileUnit` holds it back, which is exactly how a deployment whose weights are still arriving is already handled. `observedState` reports `preparing` **before systemd is believed**: no unit is started yet, so `is-active` says `inactive`, and reporting that as `stopped` would tell an operator a six-hour build had quietly given up
  - `prepare.required = false` is **refused**. Nothing would decide to run an optional build, so the phase would be declared and never happen; omitting the table is how a backend says it needs none
  - the `preparing` state and the `prepared_artifact` column were already in [`0006_fleet.sql`](../../internal/store/migrations/0006_fleet.sql), built ahead by R2-03 and until now read by nothing — so this needed **no migration**
- [x] **R6-07** `nodary backend list|show|register|remove`, gated by `allow_custom_backends`, registration recording the descriptor's SHA-256, removal refused while a deployment references it · [04 §9](../specs/04-backends.md#9-registering-a-backend)
  - *done:* a descriptor registered through `backend register --file` or `config apply` is validated, stored, carried to the nodes that use it, and rendered into their units; `backend remove` takes one back out and is refused while a deployment references it
  - **the registry is `config.Snapshot`, not a side table**, and that settled how a descriptor reaches a node. A node has no channel for one except its desired-state document ([03 §1](../specs/03-agent.md) gives the control plane no way to push), and the alternative — a file on each node — is two copies of one fact: they drift, silently, and the chain would then record a digest for a descriptor that is not the one the node ran. For a product whose deliverable is a chain an assessor reads, that is the worst available failure. It also bought `config export`, `config rollback` and `--server` for free, at the cost of one hash-preimage change paid deliberately
  - only the descriptors a node actually uses travel, so the document is the size of that node's work rather than of the fleet's catalog. The **bytes** travel rather than a decoded structure, for the reason `POST /config/apply` takes TOML: the agent parses what the operator wrote, on the version of the code about to act on it
  - **a built-in may not be shadowed, and the rule is held on both sides of the wire.** The applier refuses registering one; the agent ignores a sent descriptor that takes a built-in's name. One host in a fleet quietly running a different vLLM is not a failure anything else would catch
  - a descriptor the node cannot parse is **dropped, not fatal**. It affects the deployments that name it — which `unitFor` already refuses with a reason naming the backend — and failing the whole plan would stop the node reconciling anything, including what is serving
  - `list` and `show` are built, over `--server` as well as locally, and fall back to the built-ins on a machine with no control plane, which is where they are most often run
  - **`register` and `remove` write through `config.Apply`, not to the table**, which is what makes them four lines of flag parsing each: registering is a revision like anything else, records `config.apply` like anything else, and works over `--server` with no endpoint of its own. The three refusals that make registration more than an upsert stay in `applyBackends`, where `config apply -f` meets them too. The descriptor is parsed on this side *as well*, so a typo refuses in front of the person holding the file rather than as a 422 three hops later — and the name is taken out of the descriptor rather than off the command line, so there is no second place to write it
  - **removal sends the whole configuration back with `--prune`.** A fragment cannot express a deletion — the applier creates and updates what a document names and leaves everything else alone — and a fragment *with* prune would delete the fleet. So the verb reads live desired state, drops one entry, and applies that: the operator confirms a single `- backend NAME` line, and every other object is in the document and therefore untouched. The test that matters asserts exactly that nothing else moved
  - the audit record carries the descriptor's SHA-256 (`backends_registered`), set on the way out rather than deferred: a detail survives the rollback of the transaction it was added in, so recording a digest on a failure would state that something was registered which was not
  - the listing carries **the argument vocabulary, not just the name**, because that is the question an operator actually has before writing `params`: not "how does `max_context` reach vLLM" but "may I say `max_context` at all"
  - **`params` and `extra` stay two lists.** A name in the first is translated and means the same thing against another backend; a name in the second is passed through and does not ([04 §3](../specs/04-backends.md#3-normalize-the-few-pass-through-the-rest)). Flattening them into one would tell an operator that `gpu_layers` is portable, which is the exact belief the two-table split exists to prevent
  - the rendering is `backend.Report` in the package that owns the descriptor, not a formatter in each front end. Projections are where R2-34's constraint quietly stops being checked, because nothing calls a renderer twice
  - *found:* the descriptor tree had **toml tags and no json tags**, so `--format json` answered in Go field names — `TensorParallel` where a descriptor says `tensor_parallel`, the same defect as `policy.Profile`. Safe to tag: a deployment stores its backend's *name*, and a registered descriptor will be stored as the TOML bytes themselves, so nothing here is in a revision's hash preimage
  - *found:* `backend.ErrUnknown` is in neither front end's error table, so an unknown backend would have reached an API client as a 500 with the message withheld. Named as what it is on the way out
- [x] **R6-08** Derived images: `inherits`, a digest-pinned `from`, ordered `steps` that are not a shell, `index_url`, `timeout_s` · [04 §5](../specs/04-backends.md#5-derived-images)
  - *done:* a derive changes an image and inherits argument vocabulary, weight layout and probe from its parent, so the blast radius is an image and nothing else
  - **the schema and its refusals; nothing builds yet.** R6-09 runs the build and R6-10 records it, so `backend build` is still a named-unimplemented verb — the position `[backend.derive]` itself was in until now, and the reason it was a *refused key* rather than a parsed-and-ignored one: no operator ever wrote one and saw it accepted believing an image would be built
  - **a derive is validated instead of the ordinary form, not as well as it.** It carries a name, an `inherits` and a recipe; every field the full validation requires is one it inherits. Reached by an early branch in `Validate`, because running both would refuse `vllm-fips` for having no `api`, no `weights_layout` and no probe — all of which are the parent's
  - **"the blast radius is an image and nothing else" is enforced, not described.** A derive setting `args`, `probe`, `capabilities`, `env` or any of nine others is refused by name. §5 lists argument vocabulary, weight layout and probe; the rest are refused on the same principle rather than left for somebody to find out is load-bearing — widening this later needs a reason and is cheap, narrowing it after operators depend on a field is not
  - `image_default` is **cleared on inheritance rather than carried**. Setting it to the base would let a deployment start on the uncorrected image, which is precisely what the derive exists to prevent — the failure reached by inheriting one field too many
  - `steps` are an **argv, not a shell**: a pipe, a redirection, a `&&` or a `$(…)` is refused, because otherwise it reaches the program as an argument and the build succeeds having done something other than what was written
  - **no chains.** §5 says a derive varies a built-in, and a derive of a derive would make "what does this backend do" a walk rather than a lookup, with no cycle detection anywhere and every layer another place for a vocabulary to drift
- [x] **R6-09** Builds run on the control plane, never on a node, with a narrow egress allowlist reaching the package index and nothing else · [04 §5](../specs/04-backends.md#builds-run-on-the-control-plane)
  - *done:* a build that reaches outside its index fails rather than silently succeeding with an unexpected dependency
  - **the allowlist is a CONNECT proxy, not nftables, and the reason is DNS.** An IP allowlist has to let port 53 out for the container to resolve its index at all — and [R4d](../plans/R4d-egress-isolation.md) measured DNS as the channel that survives a route check: `<data>.attacker.example` passes every connectivity test there is. Here the container resolves *nothing*; the proxy resolves on its behalf, so there is no resolver to talk to. An IP set would also drift under any CDN-backed index
  - **it needed no new network.** A container on `nodary-isolated` already has no default route, no NAT and an empty resolver, and it can already address the host on the bridge — deliberately, because portmap's DNAT needs a route back. The proxy listens there, so the one hole §5 asks for is the one hole that already existed
  - `index_url` is **https only, refused at parse time**. A build reaches its index through a tunnel that carries TLS end to end; plain HTTP would put nodary in the middle of the bytes whose digest it is about to record. The refusal belongs where an operator is reading their own file, not an hour into a build
  - **the refusal is checked independently of the exit status.** A step can exit zero having failed to fetch something — pip falls back, a shell-less step ignores it — so a build that was refused anywhere fails even when every command succeeded. That is the difference between the `done:` line and a build that quietly ships without its correction
  - **each step is a container and the result is committed; not a Dockerfile.** BuildKit is not among the pinned components, so a Dockerfile build would need a new digest-pinned dependency and a daemon, where this needs only the containerd and nerdctl a control plane already runs LiteLLM with. It is also the shape the schema has: `steps` is an argv list, and `nerdctl run <image> <argv>` executes exactly that rather than rendering it into a `RUN` and hoping the exec form survived
  - nothing is committed from a step that failed. A recipe whose second command fails leaves **no image**, rather than one carrying half its corrections — which would run, serve, and be missing the fix it exists for
  - *known and recorded rather than discovered:* an allowlist derived from `index_url` alone is not enough for public PyPI, which serves the index from `pypi.org` and the wheels from `files.pythonhosted.org`. That is the specified behavior — "the index and nothing else" — and the refusal names the host so it reads as an allowlist decision rather than a network fault. §5's example and R6-11 both assume an internal index, which serves both from one host
  - **corrected after the fact: the proxy bound an address that does not exist yet.** It listened on the bridge's own `10.88.0.1`, which is unanswerable until CNI creates `nodary0` — and CNI creates it when a container first attaches, which is the build step that needs the proxy's address *before* it starts. So on a control plane that is not also a node — the ordinary case, since §5 puts builds here precisely to keep them off the nodes — every build failed at the bind with `cannot assign requested address`. Measured on the box rather than reasoned about: `nodary0` did not exist and the bind failed
  - the listener now takes any address and the restriction moves one layer up, to `Proxy.OnlyFrom`: a peer outside `10.88.0.0/24` is refused before it can name a host. Weaker than a socket that cannot be reached, and it is the strongest form available at bind time. It defaults on in `NewProxy` rather than being set by the caller, because a proxy behind a wildcard listener that forgot it would be one anything on the network could use
  - **verified on hardware** (nerdctl 2.3.5, containerd, real alpine 3.22, real `dl-cdn.alpinelinux.org`): a derive built end to end — pull, one `apk add --no-cache jq=1.8.2-r0` through the CONNECT proxy, commit, tag, digest resolved, tar exported. `nodary0` did not exist before the build and came up as `10.88.0.1/24` during it, which is the bind bug above, confirmed from the other side. A second recipe reaching `example.com` failed the build and named the host
  - **found in that run: an untunneled client was reported as an allowlist failure.** busybox `wget` does not tunnel — it sends an absolute-URI GET even for an https URL — and the 405 path recorded it in the same list as a disallowed host. A step that used such a client against **its own index** would have failed with "which its recipe does not name", sending an operator to add a host that was already there. The two are now separate lists with separate messages; `apk`, `pip` and `curl` all tunnel correctly
  - **found in that run: intermediates were never removed.** Each step commits `nodary-derive/<name>:step-N` and every one stayed in the store. 10MB on the alpine test; nine gigabytes a rebuild for a vLLM derive, on the control plane, with nothing that ever reads them again. Untagged after the final tag is in place, so the layers the result needs are never unreferenced even for an instant
  - **the isolation the allowlist rests on is now measured, not asserted.** With the network brought up by `EnsureIsolatedNetwork` itself, a container on `nodary-isolated` failed every way out that was tried: a raw IP (`1.1.1.1`), DNS to the host's resolver, DNS straight to a public one, the *allowed* index reached without the proxy, and `apk` with no proxy set. It reached `10.88.0.1` and nothing else — one hole, exactly the one §5 asks for. Until this run the proxy could have been decorative and no test would have noticed
  - **found in that run: the container's resolver is not empty.** [`network.go`](../../internal/agent/network.go) claimed CNI's empty `dns` block left resolv.conf naming no resolver; nerdctl copies the host's instead, and the container was handed `nameserver 10.255.255.254`. Every lookup still failed — the address is off-link and there is no route — so **the route and the drop rule are the control, not the `dns` block**, and the comments now say so. [`egress.go`](../../internal/agent/egress.go)'s DNS check is unaffected because it measures the outcome rather than trusting the configuration
  - *still unverified:* the node half. The export was removed from the store and loaded back from its tar by hand, and the digest resolved — but no agent has fetched one over the mirror, and no deployment has started on a derived image
- [x] **R6-10** `nodary backend build|rebuild` writing one audit record with the recipe SHA-256, base digest, **resulting image digest**, builder and justification · [04 §5](../specs/04-backends.md#building)
  - *done:* rebuilding is explicit; a base-image bump marks the derive `stale` and changes nothing that is serving. A failed build produces no image and replaces none, and deployments on the previous digest keep serving
  - **the build runs before the ceremony, and the ceremony is what adopts it.** `internal/core.Act` performs a change *inside* the audit transaction, and a build takes up to `timeout_s` — half an hour in §5's own example. Building there would hold a write lock on the whole control plane while every node's heartbeat queued behind it. So the build happens first, changing nothing nodary knows about, and the attested act records what it produced. That also gives the intent hash something better to bind: an operator approves **the digest that was actually built**, not a promise to build one
  - the result is **outside the configuration snapshot**, in `derived_image`. A build is a recorded act, not a configuration decision: in the snapshot it would put a build artifact into every revision's hash preimage, make each build rewrite the chain, and let `config rollback` re-pin a digest the image store may no longer hold.
