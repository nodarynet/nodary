# R3 — Gateway

**Deliverable:** auth, metering, throttling, LiteLLM stateless behind it.
**Proves:** tokens and usage.
· [00 §8](../specs/00-overview.md#8-milestones)

Deliverable level. Break these into tasks when R3 starts — R2 will have moved
some of the ground underneath.

nodary owns identity, quota, metering and audit; LiteLLM owns OpenAI
compatibility, routing, retries and fallbacks. Because identity lives in nodary,
LiteLLM runs stateless behind a single master key never exposed to clients, and
needs no database of its own. · [00 §7](../specs/00-overview.md#7-why-litellm-stays)

- [x] **R3-01** `nodary-gateway` process serving the OpenAI surface: `/v1/chat/completions`, `/v1/completions`, `/v1/embeddings`, `/v1/models` · [06 §1](../specs/06-gateway.md#1-request-path)
- [x] **R3-02** Bearer authentication resolving `nodary_sk_…` to a person; `401` for revoked, expired and suspended-user tokens; `last_used_at` recorded · [06 §2](../specs/06-gateway.md#2-authentication)
  - the **kind** is enforced, not just the credential: a personal token is refused here. [02 §4](../specs/02-enrollment.md#4-token-types) gives each prefix one purpose, and accepting a `pt` would make the credential on an operator's workstation — which can mutate the control plane — the same one any application holding an inference key uses
  - `last_used_at` goes through `internal/observed`, because an inference request authorizes no act and so has no audited mutation for the touch to ride along with
- [x] **R3-03** Per-user model allowlist; a route outside it returns `403`, and `/v1/models` returns only permitted routes rather than the full fleet · [06 §2](../specs/06-gateway.md#2-authentication)
  - **a user with no grants may call nothing.** [07 §5](../specs/07-identity-audit.md#5-control-mapping) maps this to AC-3 and AC-6 with the words "least privilege by default", and an empty allowlist meaning *every* route would make that sentence false — it would leave the role grant as the only real control and the allowlist as a restriction somebody has to remember to opt into
  - the grant is in the configuration snapshot, so it is a revision like every other administrative decision, and it is keyed by user **name** so an export survives a rebuild where the same people have different ids
- [x] **R3-04** LiteLLM deployed stateless behind a master key, its configuration generated from routes and deployments · [06 §1](../specs/06-gateway.md#1-request-path)
  - proved against **the pinned image from `components.json`**, not a schema read from documentation: the real LiteLLM starts on the generated configuration, loads the route, and refuses `/v1/models` without the master key. R3-04's real risk was that the configuration is rejected, and nothing would have known until an install
  - the client's own `Authorization` never reaches LiteLLM. It identifies a person to nodary and means nothing upstream, and forwarding a credential past the component that consumed it is how a stateless proxy acquires an identity it should not have
- [x] **R3-05** Metering: user, token, route, resolved model, deployment, prompt and completion tokens, latency, status, streamed, partial · [06 §3](../specs/06-gateway.md#3-metering)
  - **deployment and node were never written, and "resolved model" was the route name.** The columns have existed since `0006_fleet.sql` and `nodary usage --node` has filtered on one of them since R3-12, so per-node and per-GPU chargeback — most of what metering is for at this size — returned nothing, always
  - a route may have several members and **LiteLLM chooses between them**, so nothing in a request says which deployment served it. `gateway sync` now writes each member's deployment id into `model_info.id` and the gateway reads it back from `x-litellm-model-id`: the component that made the choice is the one that reports it. The node follows from the deployment, and the GPUs from `deployment_gpu`
  - the header is a **third-party contract nobody promised us**, so it is asserted against the pinned digest rather than assumed — two containers from that one image, streamed and not, and a version bump that drops or renames it fails there rather than silently returning to NULLs
  - a response with no such header attributes **nothing**. An id LiteLLM returns for a deployment this control plane does not have is recorded as given and resolved no further: dropping it would lose the only clue that the two are out of step
  - the model id is now the deployment's, not the route's. `model register` takes both names and nothing makes them equal; `nodary usage --model` already matched either, so recording the real one narrows nothing
- [x] **R3-06** Streaming usage: inject `stream_options.include_usage`, read the final usage chunk, pass the stream through otherwise untouched · [06 §3](../specs/06-gateway.md#3-metering)
  - a client cannot opt out. Opting out of usage reporting would be opting out of nodary's accounting, which makes metering advisory — and the cost is stated: a client that set `include_usage: false` now receives a usage chunk it did not ask for
  - chunks are **scanned and forwarded, never re-serialized**, and the scanner carries a partial line across writes. Asserted against a stream delivered one byte at a time, which is the case that finds an accumulator that resets per write
- [x] **R3-07** A stream that terminates early is metered from tokens observed and flagged `partial`
  - *done:* usage is never silently dropped on disconnect. If disconnection erased usage, metering would be trivially avoidable and the quota system decorative
  - *was partial:* the **flag** landed with R3a — a stream that produced no usage chunk recorded `partial = 1` rather than a silent zero. What remained was counting the tokens actually observed, which was recorded as needing a tokenizer the gateway does not have
  - *done:* **it does not need one.** Every backend this build ships — vLLM, SGLang, llama.cpp — streams token by token, so the chunks that carried generated text are the tokens generated. The count is charged against `tpm` and the daily budget, which is what closes the hole [06 §3](../specs/06-gateway.md#3-metering) names: a row that is recorded and not charged leaves the accounting honest and the budget not binding, which is the same hole by a politer route
  - **it is a count of chunks presented as a count of tokens, and the `partial` flag is what makes that honest.** A backend that batched several tokens per chunk would undercount, and prompt tokens are not knowable here at all — so the row says its accounting is incomplete rather than claiming a total it cannot stand behind. The alternative is a tokenizer per model inside the gateway: a large dependency and a second place model vocabularies have to be kept in step, bought for an estimate on an exceptional path
  - the chunk that only announces the assistant role and the one that only carries `finish_reason` carry no text and are not counted, so this bills for generation rather than for protocol. `/v1/completions` puts its text in `choices[].text` rather than `delta.content`; both are read
- [x] **R3-08** Token-bucket throttling on `rpm`, `tpm`, `daily_tokens` and `max_concurrent`, per user, per role and globally · [06 §4](../specs/06-gateway.md#4-throttling)
  - **every applicable limit binds and the most restrictive wins.** A user's own limit, their role's and the global one all apply at once. The alternative — most specific overrides — makes a global ceiling escapable by giving somebody a per-user limit, and leaves an administrator unable to cap the fleet without editing every user. The cost, stated: a per-user limit cannot *raise* anyone above a global one
  - **`tpm` is charged after the response, not before.** A request's token count does not exist until its response does, so the check is "is the bucket empty" and the debit is the observed cost. A single very large response leaves the bucket negative and delays the next request in proportion, which is what a tokens-per-minute ceiling should do
  - **a daily budget can be exceeded by at most one request**, for the same reason: admission is decided on what is already spent. Noise at a budget of a million tokens, and pinned in a test at a budget of 20 where it is glaring
  - `rpm`/`tpm`/`max_concurrent` are in-process. A restart costs at most one minute's allowance, against putting a write on every request on the single writer connection the audit chain, agent status and metering already share. `daily_tokens` is the exception and is read from the `usage` table, because a daily budget a restart forgives is not a budget
  - *note:* 06 §4's "configured UTC hour" for the daily reset has no setting anywhere in the tree. Midnight UTC is the value, and `dailyResetHour` is the one place it moves to when there is one
- [x] **R3-09** `429` carries `Retry-After` and a body naming which limit was hit, current usage and reset time
  - *done:* a bare 429 tells a user nothing actionable. The envelope's `detail` carries `limit`, `subject`, `limit_value`, `used` and `resets_in_seconds` — `subject` because a user refused by a limit they did not know about should be able to find the administrator who set it. `Retry-After` is never zero, which would invite a client straight back into the same refusal
  - `errThrottled` is its own error value rather than a denial: a 403 tells a client to stop and a 429 tells it to wait, and a client that cannot tell them apart either gives up or hammers
- [x] **R3-10** Throttle events are usage records; changing a limit is an audit record · [06 §4](../specs/06-gateway.md#4-throttling)
  - *done:* the two are never written to the same place — one is telemetry, the other an administrative act with an accountable author. A refused request is a `usage` row with status 429 and zero tokens, because it never reached a model. `limits set` was already an audited `config.apply`, and a test asserts nothing throttle-shaped reaches the chain
  - *note:* `nodary limits set` carried a warning that nothing enforced what it wrote (R3a §6). That is replaced rather than deleted: it now says every applicable limit binds and the most restrictive wins, because an operator who writes 600 and observes 100 should not have to read the gateway to find out why
  - *note:* raised as the review's second blocker · [2026-09-11 review](../review-2026-09-11.md)
- [x] **R3-11** Gateway failure behavior · [06 §5](../specs/06-gateway.md#5-failure-behavior) · [11 §4](../specs/11-failure-modes.md#4-gateway)
  - *done:* no ready deployment → `503` + `Retry-After` + alert; LiteLLM unreachable → `502` with no direct-to-deployment fallback, because that path would bypass routing and fallback logic; token revoked mid-stream → the stream completes and the next request is rejected
  - **the first row was the one that did not exist**, and [R3-14](#) is what made its absence reachable: with only ready members rendered, a route whose replicas are all still loading is simply not in the data plane's configuration, so the client got LiteLLM's own "no such model" — a permanent-sounding answer to a temporary condition. A client told *no such model* gives up; one told *not yet* comes back
  - refused **before the throttle**, so a request that cannot succeed does not spend the caller's quota on finding that out, and after the allowlist for the reason the throttle already gives: being denied a route is permanent and being throttled is not
  - read from the control plane's own tables rather than from the rendered `litellm.yaml`, which belongs to another unit and whose format the gateway has no business parsing. The cost is a **bounded window**: a deployment that has just reported ready is visible to the gateway before `nodary-gateway-sync.timer` has put it in the data plane's configuration, so for up to a minute this says "go ahead" and LiteLLM answers that it has no such model. It resolves itself, and it is the smaller of the two wrongs — the alternative is refusing a route that is in fact serving
  - `disabled` is a ready-member test here as well as in the renderer: an operator who ran `model disable` has said so, and the answer should not depend on the node having got around to reporting the stop
  - *found by it:* the gateway's own fixture built a route with **no members at all**, so every test in that file was exercising a fleet that could not have served anything
- [x] **R3-12** `nodary limits show|set` and `nodary usage show` with `--user`, `--model`, `--node`, `--group_by`, `--from`, `--to`, `--format` · [10 §1](../specs/10-cli.md#1-verbs)
- [x] **R3-13** Roll `usage` into `usage_daily` past `usage_retention_days` · [08 §3](../specs/08-data-model.md#3-retention)
  - rolled and deleted **in one transaction**, so there is no window in which the rows are gone and the total they contributed to is not yet written
  - **`usage_daily` cannot hold what `usage` can, and one unattributed request used to fail the whole pass.** `user_id` and `model_id` are nullable on the raw table and both sit in the aggregate's primary key, which a `STRICT` table makes implicitly `NOT NULL` — so a request with no principal or a body naming no model raised a constraint error that took the join tokens and the chain down with it. They roll up as `''`, which is also what makes the upsert work at all: SQL treats two nulls as distinct, so null keys would never have merged
  - it runs under the same `nodary prune` pass as R2-14 — one verb, because one audited act removing everything a retention pass removes is easier to read in the chain than three
- [x] **R3-14** Route round-robin across ready members, with health-driven membership changes honoured live · [05 §5](../specs/05-catalog.md#5-routes)
  - *was partial:* `nodary gateway sync` renders the data plane from current routes and restarts it when the running process is behind, which is the manual form of this. Live membership is what stayed open
  - *done, and the first half was a bug rather than a gap:* **every member of a route was rendered whatever its state.** LiteLLM kept an `api_base` pointed at a deployment the operator had `disable`d, at one whose card had left the bus, and at one that had never started — so a client got a connection refused from inside the data plane instead of the `503` with a `Retry-After` [06 §5](../specs/06-gateway.md#5-failure-behavior) specifies for a route with no ready member. Only members the fleet reports `ready` are rendered now
  - **`ready` already folds in health**, which is what makes this health-driven without the renderer knowing what a health probe is: `internal/agent`'s `observedState` calls a unit ready only when it is active *and* its probe answers, so a replica that goes unhealthy drops to `starting` and leaves its route on the next sync
  - the states are read **beside** the configuration snapshot rather than from it. They are observations, and putting them in the snapshot would make a heartbeat read as a configuration change · [R4a §4](../plans/R4a-agent-protocol.md)
  - `disabled` is checked separately and from the snapshot, because it is a *decision*: an operator who ran `model disable` has said so, and the route should not keep serving while the node gets around to reporting the stop
  - **live is two mechanisms, deliberately.** Membership catches up with readiness on `nodary-gateway-sync.timer`, a minute apart — a model takes minutes to load, so nothing is waiting on that. The case that has to be fast, a replica that stops answering mid-request, is handled on the request path by the router's own cooldown, which needs no restart: `num_retries`, `allowed_fails` and `cooldown_time` are now pinned in `litellm.yaml` the same way the logging settings are, because a setting this product depends on must not be whatever a future LiteLLM release defaults it to. Doing it the other way — re-rendering on every health blip — would restart the data plane and drop live requests in order to route around a replica the router is already routing around
  - the timer **runs as root, and that is why it is a unit of its own.** `nodary-server` holds the routes and deliberately cannot write `/etc/nodary` or restart a service; the process that knows asks nobody, and a small periodic act that knows nothing does the writing. It is cheap when nothing moved — `gateway sync` restarts only when the running process's configuration differs from the rendered one
  - **`simple-shuffle`, and §5's "round-robin" is honoured as "spread across ready members".** LiteLLM offers no strategy by that name; naming the discrepancy is cheaper than implementing a strict rotation in front of a router that already spreads
  - *found while pinning it:* **`RouteMember.Weight` was stored and never rendered**, so `nodary route set --add` wrote a weight that changed nothing. It reaches the router now. A configuration field an operator can set and the product ignores is worse than one that does not exist
  - it is **no longer a step to remember**: `config apply`, `config rollback` and `model register` run it themselves when the change moved a route or a deployment, because that separate step was the one people forgot — a model that starts, becomes healthy and reports ready, while every client gets a 404 from a data plane that has never heard of it. Skipped, with the command printed, when the database was named with `--db`: that is not the installed control plane, and re-rendering `/etc/nodary` from a copy would point the running data plane at something else's routes
  - it restarts on **what the running process loaded**, not on whether the file changed. Those come apart exactly when it matters: the file was written while LiteLLM was already up, so a later sync found it correct, restarted nothing, and left the data plane serving an empty model list with a good file on disk beside it — reporting success and changing nothing. The digest of what the running process started with is recorded in `/run`, which a boot clears, and a missing marker means "unknown" and restarts
  - **that decision logic was right and the restart underneath it did nothing anyway.** `systemctl enable --now` on a unit that is already active is a no-op by systemd's own semantics — it does not compare what changed, it only asks whether *a* process is up — so `gateway sync` called it, was told success, and LiteLLM kept serving the empty list it started with. Found only by testing a real end-to-end completion on hardware; every unit test used a staged install, where neither `Start` nor the now-separate `Restart` run `systemctl` at all. Fixed by giving restart its own function (`systemctl restart`, which starts a stopped unit exactly as well as it restarts a running one) and pointing `gateway sync` at it instead of `Start`
  - it is a **separate verb because the processes that know cannot write.** `nodary-server` holds the routes and runs unprivileged under `ProtectSystem=strict` with `ReadOnlyPaths=/etc/nodary`; widening that unit until it could rewrite the data plane's configuration and restart services would hand the network-facing process exactly the capability worth withholding
  - **an unresolved specification question surfaced here.** [03 §5](../specs/03-agent.md#5-egress-isolation) publishes a deployment on `127.0.0.1` *"so the container is reachable by the gateway"* — true when the gateway is on the same machine, false when it is not — while [00 §2](../specs/00-overview.md#2-topology) makes traffic to nodes agent-initiated only, so the control plane has no specified way to reach a deployment on another host. Until that is answered, `gateway sync` **skips a route on another node and names it**, rather than rendering an `api_base` that answers nothing
- [x] **R3-15** The metering record schema is closed — no free-text body field exists to write into · [pivot §3](../plans/pivot-cmmc.md#the-guarantee-is-structural-not-documentary)
  - *done:* a test fails if request or completion content reaches the database or a log. "nodary records that a request happened, never what it said" is a structural guarantee, made unreachable in the same way as [the audit seam](README.md#cross-cutting-constraints) rather than merely discouraged
  - **two tests, because one would not be enough.** A canary prompt goes through the gateway — streaming, non-streaming, and two error paths — and every byte of the database, its write-ahead log and the gateway's log is searched for it. That proves today's code. A second test pins the record's field set and the table's column list, which proves there is nowhere to write one: a guarantee that depends on every future author remembering it is not structural
  - *deps:* R3-05
- [x] **R3-16** LiteLLM's configuration is rendered with request logging pinned off, and the pinning is asserted · [pivot §3](../plans/pivot-cmmc.md#litellm-is-now-a-compliance-surface)
  - *done:* asserted continuously rather than configured once, on the same principle as [egress verification](../specs/03-agent.md#5-egress-isolation). Inside a CUI boundary, "LiteLLM begins writing request bodies somewhere by default" is an incident rather than a nuisance
  - six settings plus three empty callback lists, each written explicitly **even where it is already the default**, because a configuration that omits a setting inherits whatever the next default is. `AssertLoggingOff` checks the rendered bytes rather than trusting the renderer, and the gateway calls it before using a configuration
  - *deps:* R3-04

data plane with LiteLLM retained; [06 §7](../specs/06-gateway.md#7-the-data-plane) is the
