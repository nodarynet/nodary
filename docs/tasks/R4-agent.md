# R4 — Agent

**Deliverable:** enroll, long-poll, reconcile, systemd units, egress isolation, staging.
**Proves:** nodes run without an orchestrator.
· [00 §8](../specs/00-overview.md#8-milestones)

Deliverable level. Break these into tasks when R4 starts.

Node guardrails ([12](../specs/12-node-guardrails.md)) are not a milestone of
their own and land here: the agent checks the desired state against `node.toml`
before reconciling, so the check belongs with the reconcile loop. Adding it
afterwards would mean threading a refusal path through code written to assume it
never refuses. · [00 §8](../specs/00-overview.md#8-milestones)

## Enrollment and trust

- [x] **R4-01** `POST /api/v1/enroll` — CSR plus join token returns a 90-day client certificate; the only unauthenticated agent endpoint · [02 §1](../specs/02-enrollment.md#1-flow)
- [x] **R4-02** CA fingerprint pinning: the agent fetches the CA certificate on first contact and refuses it unless the fingerprint matches; `--ca-fingerprint` is required for a network install · [02 §1](../specs/02-enrollment.md#1-flow)
  - *done:* the pin is checked **inside the handshake** (`VerifyPeerCertificate`), not by fetching the certificate over an unverified connection and reconnecting. Same guarantee, one connection, and no window between the check and the use. A mismatch surfaces as `agent.ErrPin` rather than a transport error, because a connection that succeeded to the wrong server is an incident and not something to retry
- [x] **R4-03** Join tokens: `nodary token join --ttl --uses`, single-use by default, burned on success, minting audited · [02 §4](../specs/02-enrollment.md#4-token-types)
  - *done:* a replayed token is rejected · [11 §3](../specs/11-failure-modes.md#3-security-controls)
  - the redemption is one `UPDATE … WHERE uses_left > 0 AND expires_at > ?`; the decrement **is** the check. A SELECT-then-UPDATE would be safe today only because `store.WriteTx` serializes writers, which is safety by accident
- [x] **R4-04** Approval as a separate step: a `pending` node receives an empty desired state — it can heartbeat, it cannot serve · [02 §2](../specs/02-enrollment.md#2-why-approval-is-a-separate-step)
  - the offer is carried in the **preview**, which `core.Act` hashes into `intent_hash` and writes into the record. Terms recorded beside the record rather than inside its hash would not be covered by anything
  - *done:* the approval record names the administrator, carries their justification, and records the node's advertised offer and constraints in the same record. Neither side can later claim terms the other did not see
- [x] **R4-05** Certificate lifecycle: renewal at two-thirds of lifetime over the existing mTLS channel; a node offline past expiry must re-enroll · [02 §3](../specs/02-enrollment.md#3-certificate-lifecycle)
  - *done:* `POST /api/v1/agent/renew` under mTLS, and the agent renewing from its poll loop. The re-enrollment half was already built — `nodeCertExpiry` refuses a name whose recorded certificate is still valid, and permits it once expired
  - **the request carries no node name.** Identity is the client certificate `agentNode` has already checked against the recorded fingerprint; a name in the body would be a second, weaker claim beside a strong one, and the weak one is the one an attacker chooses
  - **the schedule is read from the certificate, not from a constant.** `renewalAt` computes two thirds of `NotAfter - NotBefore`, so a control plane that starts issuing a different lifetime moves every agent's schedule with it and nothing has to agree about the number
  - superseding and recording the new expiry are one `UPDATE`, so there is no instant where the row names one certificate's fingerprint and another's lifetime. The refusal path already existed and now has a second producer
  - a failed renewal retries hourly rather than on every poll: the first attempt is thirty days before expiry on the ninety-day default, so there are hundreds of chances and no reason to spend forty thousand of them
  - *note:* `replacePair` is two atomic writes, not one atomic operation. A crash between the renames leaves a new certificate beside an old key, and the recovery is 02 §3's re-enrollment. The window is two syscalls wide; closing it means holding both pairs and choosing at startup, which is more machinery than that is worth. Marked `ponytail:` in place
  - *note:* the load-bearing test is `TestTheNodeRenewsAgainstTheRealControlPlane` — the node's own enrollment and renewal against the real endpoint. A URL typo or a mismatched JSON field passes every one-sided test and then fails sixty days after an install; it was verified to fail when the path is broken
  - *note:* raised as the review's first blocker · [2026-09-11 review](../review-2026-09-11.md)
- [x] **R4-06** `nodary node revoke` and node-side `nodary node leave` · [12 §5](../specs/12-node-guardrails.md#5-decommissioning)
  - *done:* `leave` works without the control plane being reachable — the common case is precisely that something has gone wrong. It opens no database, reaches no server and writes no audit record, because a GPU node has none of those on it: it stops the deployments, stops the agent, and destroys the credentials that made the machine a node
  - *done, and it was mostly already built:* `revoke` only ever needed the verb. `internal/api`'s `agentNode` has refused a `departed` node's certificate since R4-01 and nothing could put a node in that state, so the enforcement sat there unreachable. The transition is `cmdNodeTransition` with a third row rather than a second implementation, and `departed_at` is written with it because 0006_fleet.sql pairs them in a CHECK — a machine that left without a date is a record that cannot be read back as history
  - **the node does not announce its own departure, deliberately.** A node claiming it has left is a claim the control plane would have to trust from the machine least able to make it, and 12 §5's "the control plane marks it `departed`" is `revoke`, an administrator's audited act from the side that holds the chain. `leave` prints that command rather than pretending the fleet has been told
  - *found while building it:* `nodary node drain` moved a node's state and changed nothing observable — the gateway's route rendering never consulted node state, so a drained or revoked node kept receiving traffic until its containers stopped underneath it. Fixed where the rendering actually happens, which was not where it looked: `internal/gateway`'s `ConfigFor` was a second copy of that logic with **no callers at all**, so the fix had to go into `internal/cli/gatewaysync.go` and the dead copy is deleted rather than left for the next person to fix by mistake

## Protocol

- [x] **R4-07** `GET /api/v1/agent/desired?rev=N` long-poll, blocking up to 60s · [03 §1](../specs/03-agent.md#1-transport)
- [x] **R4-08** The desired-state document: a complete end state, with no imperative commands anywhere in the protocol · [03 §2](../specs/03-agent.md#2-desired-state-document)
- [x] **R4-09** `POST /api/v1/agent/status` every 15s — inventory, unit states, staging progress; node marked `stale` after 60s of silence · [11 §1](../specs/11-failure-modes.md#1-control-plane-and-agent)
  - *done:* `stale` is **derived at read time and never stored**. Storing it needs a sweeper, and a sweeper leaves a window where the database says `ready` about a node gone for a minute. It also keeps staleness out of the configuration snapshot, where a missed heartbeat would otherwise show up as a configuration change
  - the heartbeat writes through `internal/observed` and produces **no audit record**. That package is the one directory besides `store` and `audit` that `TestNothingBypassesTheSeam` allows, and its package comment carries the rule it exists under · [R4a §4](../plans/R4a-agent-protocol.md)
  - **that rule was prose, and now it is a test.** The package comment said each statement names its columns explicitly *"so it can be reviewed against the rule above by reading it"* — a control performed by whoever remembers to perform it, in the one directory the audit gate exempts. `rule_test.go` scans the package's own source for writes and holds them to an allowlist of tables with a reason each, plus a list of columns that are decisions even on an allowed table (`node.state`, `token.revoked_at`, `deployment.params_json`). Verified by injecting a write to `user`, a write to `audit`, and an `UPDATE node SET state` — each is caught by the test that should catch it
  - the allowlist is also held to being **used**: a permitted table nothing writes is removed, because an unexercised permission reads as precedent for adding one
- [x] **R4-10** `POST /api/v1/agent/events` with a bounded queue that spills to disk; an overflow is itself recorded · [07 §3](../specs/07-identity-audit.md#3-the-audit-chain)
  - **a heartbeat carries state and an event carries what happened**, and the difference is what the chain is for. `nodary node show` can say a deployment is failed; only an event says it failed at 04:12, recovered at 04:19 and failed again at 04:31 — which, in a report of the current state, is indistinguishable from having been failed all along. A node's egress verdict going from compliant to breached and back leaves no trace at all in the level, and [11 §3](../specs/11-failure-modes.md) calls a failing assertion a critical alert. An alert that exists only while it is still true is one nobody can review afterwards
  - **edge, not level.** The first sighting of a deployment is not a change, or a restarted agent would write an event for everything it is already running — noise at exactly the moment somebody is reading the chain
  - **the node is the actor**, because it is: nobody asked for a deployment to fail, and attributing it to the administrator who last touched the model would put somebody's name on a thing they did not do. The action must begin with `node.`, refused otherwise — the vocabulary is what an operator filters the chain by, and a node that could choose any action could write `user.delete` into it
  - **two clocks, kept apart.** The record's timestamp is the control plane's, when it wrote the record; `node_time` is the node's, when the thing happened. A node unreachable for an hour delivers an hour-old event, and collapsing them puts the wrong time on it — while ordering the chain by the node's clock would let one wrong clock write records out of sequence
  - *the bound, and the fact that there is one:* [11 §1](../specs/11-failure-modes.md#1-control-plane-and-agent) makes this a named failure mode. The oldest events spill to a 4MB file and a full buffer drops, because a buffer that grows until the disk is full takes the staged weights with it and a node that cannot stage cannot serve. **The drop is itself an event**, reported once and ahead of what survived it, which is what keeps a gap in the chain from reading as a quiet period
  - nothing leaves the queue until the control plane has accepted it, and a partial acceptance removes exactly what was accepted — the endpoint answers with a count rather than a status alone, so a chain that stopped taking records halfway through a batch does not cost the remainder
  - *known and bounded:* delivery is **at-least-once**. The idempotency wrapper cannot help — it scopes a key to a principal resolved from a session or a bearer token, and this caller presents a client certificate — so a batch whose response was lost is sent again and an append-only chain cannot retract the first copy. Each event carries a node-minted `event_id` instead, so the two are recognisable as one event rather than as two things happening
- [x] **R4-11** Protocol version handling: an agent outside the server's supported range stops reconciling, keeps running what is already up, and reports `incompatible` · [03 §4](../specs/03-agent.md#4-version-skew)
  - *done:* it does not guess
  - **there was no range, and that is what "reports `incompatible`" was missing.** The control plane held one number and *refused* any heartbeat that did not match it — so an incompatible agent went `stale` sixty seconds later, and from the control plane an agent mid-upgrade and an unplugged machine were the same picture while being completely different problems. It is now recorded as having checked in, and nothing more
  - **nothing more** is the load-bearing half. A protocol version governs the report's *shape*, so a document from a version this build does not know is one whose inventory, unit states and staging progress it cannot honestly claim to have read; writing them anyway would put guesses in the fleet view. [`observed.Seen`](../../internal/observed/observed.go) writes the three columns whose meaning cannot move between versions, because they are what the versions are negotiated with: when we heard from it, what it says it is, and which protocol it speaks
  - the agent compares itself against the **advertised range**, not against the number the control plane speaks. That is the whole reason §4 asks for a range: a control plane upgraded to 2 that still accepts 1 is every control plane mid-rollout, and an agent comparing against one number would stop reconciling on all of them — turning a routine upgrade into exactly the fleet-wide outage this check exists to prevent. A control plane old enough to advertise no range is compared the only way what it said permits
  - *found while building it:* **`node.protocol` recorded the server's number, not the agent's.** Every node in the fleet therefore reported as current, and the derived verdict could never be anything but "compatible". Invisible until now because the endpoint refused every mismatch — except for an agent that sent no protocol field at all, which was recorded as speaking ours
  - an agent that names **no** protocol is supported, not incompatible: that is an agent old enough to have sent none, which is precisely the one an operator has to keep seeing in order to upgrade it
  - `incompatible` is derived at read time from what the node last reported, the same as `stale` and for the same reason — it is true whether or not anything wrote it down. `nodary node list` reports it *before* staleness, because an incompatible node is not stale: it keeps heartbeating, so from a listing that only reports silence it looks perfectly healthy while nothing it is told to do happens
- [x] **R4-12** Reconnect behavior: exponential backoff with jitter; on reconnect the agent reconciles forward and never replays intermediate revisions · [11 §1](../specs/11-failure-modes.md#1-control-plane-and-agent)
  - full jitter — a uniform draw from `[0, backoff)`. Anything narrower leaves a fleet's retries correlated, and arriving together the moment a control plane recovers is the second outage

## Guardrails

- [x] **R4-13** `/etc/nodary/node.toml` parsing; every field optional, an absent `[limits]` offering the whole machine · [12 §2](../specs/12-node-guardrails.md#2-the-file)
  - the offer it produces is what enrollment advertises. It was parsed and **reported and nothing more** until R4-14 evaluated it against the desired state; what stays open of the file is `window.maintenance` (R4-40) · [mvp §6](../plans/mvp.md#6-what-an-mvp-install-cannot-claim)
  - an unknown key is refused rather than ignored. Here more than anywhere else: an operator who misspells `gpu_indices` and is not told believes a GPU is withheld that is in fact on offer
  - an absent `gpu_indices` and an empty one are different answers, and TOML tells them apart. Collapsing them would turn "offer nothing" into "offer everything"
- [x] **R4-14** `evaluate` runs before any side effect · [03 §3](../specs/03-agent.md#3-reconcile-loop)
  - *done:* an agent never partially applies a document it is going to refuse — a half-applied change is worse than a rejected one
  - **the guardrails were parsed, validated, advertised, and evaluated against nothing.** A control plane could place a backend the node excluded, a VRAM fraction above its ceiling, or more deployments than it said it would take, and the node ran all of it — which is what made [00 §5](../specs/00-overview.md)'s trust-boundary table untrue
  - three limits are evaluated, and `Build` states the verdict before `unitFor` so a placement node.toml will not have is never first reported as an impossibility: `allow.backends`, `max_vram_fraction` (read out of the deployment's own params), and `max_deployments`, counted against what the plan has **accepted** so something refused for another reason occupies no slot
  - **`gpu_indices` is deliberately not re-checked.** `Advertise` narrows the offer and `Daemon.reconcile` passes that narrowed set as `PlanOptions.Present`, so `unitFor` already refuses a card the node withheld. A second answer to a question that already has one is how the two come to disagree
  - the cap falls on the **last placements by id**, because the document arrives `ORDER BY id`. Stable between cycles is the property that matters: an operator given a moving target fixes the wrong one
  - *scope, said plainly:* `allow.prepare_jobs` gates a `[backend.prepare]` step no descriptor in this build has (R6-02), and `allow.package_install` and `allow.reboot` gate actions no code path performs — nodary never initiates a reboot under either `reboot_policy`. There is nothing yet to refuse. `window.maintenance` is the one real omission and has its own row below
- [x] **R4-15** Refusals are recorded, surfaced against the node, and **not** retried · [12 §1](../specs/12-node-guardrails.md#1-where-they-apply)
  - *done:* a limit being hit repeatedly is something an operator sees, not something the system grinds against
  - *done:* the mechanism, end to end — `Plan.Refused` → the heartbeat → the `refusal` table ([R2-02](R2-control-plane.md), `0017_refusal.sql`) → `nodary node show`. `Build` has computed refusals since R4-18 and they went to the node's own journal and stopped there, so a deployment the node would never run appeared to an operator as one stuck in `defined` with no reason given anywhere — on a machine they may have no shell on
  - the set is **replaced** every heartbeat rather than appended to: a refusal is a standing condition recomputed each reconcile, not an event, so one that stops being reported has stopped applying. Appending would bury a month of them under two hundred thousand copies of one sentence, which is the reasoning `internal/observed` gives for keeping telemetry out of the audit chain, applied to its own table
  - *scope, said plainly:* these are the refusals this build produces — an unknown backend, a GPU not on offer, a deployment with no image. The **guardrail** evaluation of [12 §1](../specs/12-node-guardrails.md#1-where-they-apply) is R4-14, and it landed travelling this same pipe exactly as predicted: the only addition was a `kind` column, because a guardrail verdict about a *running* deployment is not a refusal
  - *deviation from 12 §1, recorded rather than skipped quietly:* the spec also says a refusal is "written to the audit chain". It is not, and one per heartbeat would be 5,760 records a day for one misconfigured deployment. Writing one only on the transition into a refusal is the shape that would honor both, and it is not built
- [x] **R4-16** A guardrail narrowing under a running deployment reports `out_of_policy` and does not kill it · [12 §3](../specs/12-node-guardrails.md#3-editing-a-live-node)
  - *done:* editing a config file never terminates a serving model. A guardrail nobody dares touch is not a guardrail
  - **R4-14 could not land without this, and that is a finding rather than a preference.** A guardrail verdict produces no `Unit`, and `Reconcile`'s stop loop stops every `nodary-model@` instance the plan does not name — so enforcing guardrails alone would have meant that editing `node.toml` terminated a model mid-request. Measured, not reasoned about: removing the one line that adds a running out-of-policy unit to `wanted` makes the test stop it
  - so the verdict is split across the two halves. `Build` says which placements node.toml narrows out (`Plan.OutOfPolicy`) and cannot say more, because it never touches systemd; `Reconcile` — which does — decides between a placement that is serving (left alone, reported `out_of_policy`) and one that never started (an ordinary refusal). `agent plan` prints the verdict as `outside node.toml` for the same reason: a preview has not looked at what is running and must not claim to have
  - a deployment that leaves the document entirely is **still stopped**. The protection covers what a guardrail narrowed under, and must not become a way for anything absent from the plan to survive
  - the two verdicts share the `refusal` table and its wholesale replace, and are kept apart by a `kind` column (`0018_refusal_kind.sql`) rather than by wording: they read alike and mean opposite things about whether anything is serving. `nodary node show` prints them as separate tables, because the action differs — one is a configuration to change, the other a decision about a model that is already answering requests
- [x] **R4-01a** The GPU probe resolves `nvidia-smi` rather than looking it up on PATH
  - the WSL2 trap again, in the one place it had not been fixed. `/usr/lib/wsl/lib` is added by a login profile and dropped by both sudo's `secure_path` and a systemd unit's PATH, so the agent found no card, **enrolled advertising an empty offer**, and every deployment was refused with `GPU 0 is not on this node's offer` — on a host whose own `nodary doctor` reported an RTX 5090, because doctor resolved and this did not
  - the offer is written **only at enrollment** ([02](../specs/02-enrollment.md)), deliberately — it is what the node put on the table, and [02 §1](../specs/02-enrollment.md)'s "neither side can later claim terms the other did not see" depends on it not moving under the approval that agreed to it
  - the *observed* inventory is a different column and the heartbeat does refresh it, so a node that enrolled blind reports its real GPUs within fifteen seconds and the agent's own placement check uses live inventory. What stays stale is `offer_json`, the agreed terms — and correcting **that** is re-enrollment, which [02 §3](../specs/02-enrollment.md#3-certificate-lifecycle) gates behind certificate expiry on purpose. Recorded rather than "fixed": silently rewriting agreed terms is the thing the gate exists to prevent
- [x] **R4-40** `window.maintenance` is when an `out_of_policy` deployment is stopped · [12 §2](../specs/12-node-guardrails.md#2-the-file), [12 §3](../specs/12-node-guardrails.md#3-editing-a-live-node)
  - split out of R4-14 rather than folded into it, because it is a different mechanism with a different hazard. The other limits decide whether a *placement* may run and are answered from the document; this one gates an *action* on a clock, inside `Reconcile`
  - **the hazard was what needed deciding, not the parsing**, and the decision narrowed the feature. 12 §2's table said the window refused any stop, restart or restage outside it — which would mean `nodary node drain` stops nothing until Saturday on a machine an operator is draining *because it is failing*. `node drain`, `model disable` and `model restart` are explicit, audited decisions somebody is making now; deferring those is a footgun whose only defense is remembering a flag at the moment you are in a hurry. **The spec's table row was narrowed** rather than the dangerous version built
  - what the window schedules is the disruption **nobody asked for**, and after R4-14/R4-16 there is exactly one: a guardrail narrowed under a running deployment. 12 §3 already said so — such a deployment waits "for the control plane to withdraw it, **or for the next maintenance window**" — and that second half had no implementation, so it waited forever: the node restated the verdict every minute about something it went on running
  - **an absent window is never open.** Reading "no window" as "any time" would turn the safest configuration into the most disruptive one, and it is what keeps every `node.toml` written before this behaving exactly as it did
  - the clock is read in `Build`, which already holds `node.toml`, so the plan carries a decision and `Reconcile` carries no dependency on the time of day. Leaving the unit out of `wanted` is the whole change; the stop loop already does the rest
  - **the zone is resolved at load, not at use.** Measured: Go's database resolves `EST`, `CET` and `MST` and does *not* resolve `PST` or `AEST` — so half the abbreviations somebody reaches for first are not zones at all, and without the check they would parse, validate, advertise, and then match no minute of any week. A window that silently never opens is a bug found at 2am on a Saturday
  - a window whose end precedes its start **wraps past midnight**, because `sat 22:00-02:00` is the shape a maintenance window most often has; one that opens and closes at the same minute is refused as the typo it is
  - it needed nothing new on the wire: the verdict is what `out_of_policy` already carries (R4-16), and once the unit is stopped the next cycle reports it as an ordinary refusal, which is what it then is
- [ ] **R4-41** `agent.GPU` carries the card's vendor, detected at enrollment and written into the offer · [R6a §1](../plans/R6a-a-second-gpu-vendor.md), [R6a §4](../plans/R6a-a-second-gpu-vendor.md)
  - enumeration stays **per vendor**, `nvidia-smi` first and `/sys/class/drm` second. Measured: `/sys/class/drm` holds no cards at all on WSL2 — the only device is `/dev/dxg` — so a sysfs enumerator that replaced `nvidia-smi` would report an empty offer on the one machine this fleet has been proved against, which is R4-01a reintroduced by a refactor that looked like a generalisation
  - an **absent vendor reads as `nvidia`**. [02 §3](../specs/02-enrollment.md#3-certificate-lifecycle) gates restating an offer behind certificate expiry, so every node enrolled before this keeps the offer it made; "unknown" would strand them
  - it belongs in the **offer** rather than in a probe at deployment time, because [02 §1](../specs/02-enrollment.md) makes the offer what the node put on the table and `node approve` renders it into the preview the chain records. A card whose vendor nobody agreed to is an approval that described something else
- [ ] **R4-42** Preflight's GPU checks ask the vendor that answered · [R6a §5](../plans/R6a-a-second-gpu-vendor.md)
  - five checks, not one: `checkDriver`, `checkGPUs`, `checkRAMPerGPU`, `checkFreeVRAM` and `checkContainerToolkit`, all of which run `nvidia-smi` or `nvidia-ctk` and the first and last of which are **hard failures for a node**
  - the toolkit check is the one that changes shape rather than wording. CDI is how a GPU reaches a container *on NVIDIA*; `--device /dev/dri/renderD*` needs no toolkit at all, so the harder vendor is the one already built
- [x] **R4-17** Reported inventory is the offer, not the machine: a four-GPU host offering three appears as a three-GPU node · [12 §4](../specs/12-node-guardrails.md#4-reported-inventory)
  - the narrowing happens **on the node**, before the wire, so the control plane is never told the fourth card exists and cannot place work on it. Filtering at the far end would leave the knowledge on the wrong side of the boundary

## Reconcile and runtime

- [x] **R4-18** The reconcile loop: idempotent, convergent, observing actual state rather than assuming it caused it · [03 §3](../specs/03-agent.md#3-reconcile-loop)
  - *done:* the fixed ordering holds — weights before prepare, prepare before start, stop before weight removal, GPU released before reassignment
  - the env file is compared before it is written, and only a real change restarts a unit. The failure this prevents is not a wasted write: it is a model server restarting every fifteen seconds forever, dropping in-flight requests each time
  - the loop stops `nodary-model@*` and nothing else. A node is rarely only a nodary node ([12](../specs/12-node-guardrails.md)), and stopping "anything unrecognized" on a machine somebody else also uses is the most destructive thing this codebase could do. The scoping is in the `list-units` glob, not in a filter applied afterwards
  - `prepare` is R6-06 and is not in this build, so the ordering rule it belongs to is untested rather than satisfied
- [x] **R4-23a** The `--gpus` value follows what the host's CDI specification declares
  - nerdctl resolves `--gpus device=0` to the CDI device `nvidia.com/gpu=0`, and **on WSL2 no such device exists**: there is no `/dev/nvidia0`, only `/dev/dxg`, so `nvidia-ctk cdi generate` emits a single device named `all`. Every deployment died in a restart loop with `CDI device injection failed: unresolvable CDI devices nvidia.com/gpu=0`, on a host where `nerdctl run --gpus all` works — the same fact R4-23's note records about the assignment check, reaching the argv instead
  - `all` is used **only when it is equivalent** — every GPU the node offers is assigned to this deployment. A subset is **refused, not widened**: [03 §7](../specs/03-agent.md#7-gpu-assignment-health-restart-reboot) makes assignment explicit, and handing a container three cards when it was given one is a different deployment, not a degraded one
  - an unreadable specification changes nothing. Preflight already refuses a node with no toolkit, and guessing `all` on a host whose specification nobody read would be the widening above
- [x] **R4-19** `nodary-model@.service` template and `/etc/nodary/deployments/<id>.env`; the agent writes the env file and calls `systemctl` and holds no supervision logic of its own · [03 §6](../specs/03-agent.md#6-unit-template)
  - **the template in 03 §6 was wrong and is corrected.** `${NODARY_ARGS}` passes the whole argument list as a *single* argument; systemd splits `$FOO` at whitespace and never splits `${FOO}`. The model server would have received its entire argv as one string and exited on an unrecognized argument — on a GPU host, as a container that will not start, a long way from the cause. Measured on systemd 255 and asserted in both directions
  - the agent rewrites the template when it drifts. The variable names there and in the plan are one contract in two places, and a hand-edited template that no longer reads `NODARY_ARGS` starts a model server with no arguments at all
- [x] **R4-20a** `ready` means **serving**, not merely active
  - [03 §7](../specs/03-agent.md#7-gpu-assignment-health-restart-reboot) waits for `ready` and counts ready replicas before a rolling restart may proceed, so it has to mean *able to serve*. The unit is `Type=exec` running `nerdctl run`, which systemd calls active the instant the binary is exec'd — while it is still pulling twenty gigabytes, and again while the model loads weights
  - reported ready anyway, this told an operator a deployment was serving **when no container existed**, and would let a rolling restart count a still-pulling replica as the last live one. Health decides it now; the unit being up only gets `starting`
- [x] **R4-20** Health polling every 10s; three consecutive failures mark `unhealthy` and remove the deployment from its route · [03 §7](../specs/03-agent.md#7-gpu-assignment-health-restart-reboot)
  - the agent **reports** and does not act. 03 §7 gives the two halves to different sides: the agent marks it, the control plane removes it from its route. A route is fleet state — another node may hold the last ready replica — so a node withdrawing itself would be deciding on information it does not have. The route half is R3
  - below the threshold it is `unknown`, never `healthy`: reporting healthy after a probe this node just watched fail would assert something it saw not happen. One success clears the count, because every extra probe is time a serving deployment spends out of its route

- [x] **R4-21** Failure handling: crash-loop backoff, `failed` after N restarts in a window, last 100 log lines captured, `ready_timeout_s` enforced · [11 §2](../specs/11-failure-modes.md#2-models-and-deployments)
  - **systemd does the counting.** [11 §2](../specs/11-failure-modes.md#2-models-and-deployments) asks for "systemd backs off; marked `failed` after N restarts in a window", and `StartLimitIntervalSec`/`StartLimitBurst` are exactly that — so the agent counts nothing and only has to observe the outcome

The limit was unreachable, so a crash-looping model server restarted every ten seconds forever and nothing ever called it failed. Five in five minutes now: a transient crash costs one and recovers, a server that cannot start burns the budget and stops
  - *done:* `failed` and `stopped` are different facts again. `isActive` compared `systemctl is-active`'s output against "active" and dropped the rest, so a unit systemd had given up on and one an operator had stopped cleanly arrived identically — the first has to stay stopped, the second has to be started again, and nothing could tell them apart

Measured from the first unanswered probe and cleared for good by the first answered one, so it means "has not served yet" and not "is unwell now" — a deployment that served for a week and then fell over is `unhealthy` (R4-20) and must never be failed against a startup timeout it cleared long ago

- [x] **R4-22** Rolling restart that never drops the last ready replica; fewer than two replicas requires `--allow-downtime` · [03 §7](../specs/03-agent.md#7-gpu-assignment-health-restart-reboot)
  - **the sequencing is the control plane's, and it has to be.** Replicas of one model live on different hosts — putting two on one buys no availability — and no agent can see another's, so every node cycling on its own schedule is the model going down. [03 §1](../specs/03-agent.md#1-transport) gives the control plane no way to push, so what it does instead is decline to **offer** the next restart: [`fleet.OfferedRestarts`](../../internal/fleet/transition.go) withholds a request while an earlier one in the same roll is outstanding
  - **the verb returns immediately.** A long-running command would have to stay alive across minutes of restarts, would leave a half-written roll behind whenever it was interrupted, and could not work over `--server` without holding a request open the whole time. The whole roll is written in one transaction — one audited act, one justification, one ceremony — and the ordering lives in the rows
  - **done means serving, not cycled**, and that is the half that lives on the node. The agent reports a restart finished only once the deployment is serving again ([`restartFinished`](../../internal/agent/run.go)); reporting on the cycle would let the next node stop its copy while this one was still starting, which is the outage the roll exists to avoid, reached by the mechanism meant to prevent it. Readiness is something only the node can see, so the waiting is there
  - *a roll halts by itself.* A replica that does not come back is never reported done, so its row is never cleared, so nothing after it is ever offered and the remainder keeps serving — §7's "halt, leave remainder running, report" with nothing to implement
  - **`--node` is optional again.** It was required on the reasoning that a restart is one node's act, which is true of cycling a unit and false of the thing §7 describes: it iterates over the replicas of a *model*, and that is where the guarantee comes from. Named, it narrows the roll to one host's copies; omitted, it takes every replica in a fixed order — by node, then id, so "it stopped at the second replica" names the same machine every time it is said
  - `--allow-downtime` is not paternalism: restarting a single-replica model is ordinary. What it prevents is doing it **without noticing**, because the same command is safe on a model with four replicas and an outage on a model with one, and which you have is not visible in what you typed. A model with nothing serving is exempt — that is the state somebody most wants to restart out of
  - *not built, and named rather than implied:* the explicit "remove from route → drain" step. [R3-14](R3-gateway.md) renders only ready members and re-renders on a one-minute timer, and LiteLLM's own retry and cooldown cover the request path, so a replica leaves the route without being taken out of it — within a minute rather than immediately. `ExecStop` already allows 30s for in-flight requests. The guarantee §7 states is delivered by the sequencing; the drain is approximate
  - verified by injecting all three ways it stops being a roll: every replica offered at once, the node acknowledging on the cycle, and the downtime gate removed
- [x] **R4-23** GPU assignment double-checked on the node before start; a conflict is refused and reported · [03 §7](../specs/03-agent.md#7-gpu-assignment-health-restart-reboot)
  - *done:* `Build` refuses a deployment claiming a card another deployment in the same plan already took, names the card and the holder, and reports it like any other refusal. Defense in depth — the control plane's guarantee is `deployment_gpu_exclusive`, a unique index — and that is the point: [11 §2](../specs/11-failure-modes.md#2-models-and-deployments) makes two deployments on one card a named failure mode, and a node that trusted the document would start both and make each of them slow rather than making one of them refuse

  - *found by it:* two test fixtures placed overlapping deployments on one node, which is the state this refuses
  - *done:* the check does **not** test for `/dev/nvidia<index>`. A WSL2 node has no such node — the only device is `/dev/dxg`, and `nvidia-smi -L` still reports the card correctly — so a device-node test passes vacuously on native Linux and fails wrongly on every WSL2 host. The runtime does enforce the index and says so loudly (`error: 1: unknown device`), which is the signal to check · [spike §5](../spike-fips-and-manifest.md#wsl2-binds-a-gpu-through-devdxg-and-there-is-no-devnvidia)
- [x] **R4-24** `reboot_policy` detection and enforcement — `manual-console` for an encrypted root with no network unlock, `host-managed` on WSL2; the agent never initiates a reboot on either · [03 §7](../specs/03-agent.md#reboot-safety)
  - **the safe answer is the one given whenever the question cannot be answered.** `unattended` is claimed only where the root filesystem is positively established as coming back without a person; a tree that cannot be read, a root device that cannot be resolved, or a key source this build does not recognise are all `manual-console`. Getting that backwards tells an operator a machine in a locked rack will come back, and it does not
  - *what the blanket default cost:* every host that was not WSL2 reported `manual-console`, which is safe and is a false alarm on every ordinary server — and a warning that fires on every machine is one nobody reads
  - **the device stack is walked, not sampled.** LVM-on-LUKS is the ordinary encrypted install: root is an LVM volume whose physical volume sits on a crypt device, so the device mounted on `/` reports `LVM-…` and a check that stopped there calls the disk clear. Resolved by **device number** out of `/proc/self/mountinfo` rather than by the path, because that path is `/dev/mapper/vg-root` on one host, `/dev/dm-0` on the next and a `by-uuid` symlink on a third, and `/sys/dev/block` is indexed by exactly the number
  - **every crypt layer, not any.** A host whose root unlocks from a TPM and whose second volume prompts still stops at a prompt; reporting the automatic half is reporting the wrong half. The two automatic signals are narrow on purpose — a key file in `/etc/crypttab`'s third field, and `tpm2-device=` in its options — because a key source this build cannot recognise is one it cannot promise anything about
  - *found while building it:* **preflight already answered this question, differently.** `checkEncryptedRoot` read `/etc/crypttab` and never looked at the root device, so an encrypted *data* disk beside a plain root reported `manual-console`, and an encrypted root whose unlock is configured only in the initramfs reported `unattended` — the direction that strands a machine. It also took "any entry with a key file" for the whole host. The detection lives in [`internal/preflight`](../../internal/preflight/rebootpolicy.go) now and `internal/agent` calls it, because agent already imports preflight and the cycle only runs one way; a test holds the check and the offer to one answer
  - verified by injecting the three ways it goes wrong in the dangerous direction: the stack not walked, "any" in place of "every", and an unreadable host read as fine
- [x] **R4-25** A GPU falling off the bus marks affected deployments `failed` and flags the node, and **never** triggers an automatic reboot · [11 §2](../specs/11-failure-modes.md#2-models-and-deployments)
  - *done:* the node compares what the driver reports now against what each deployment was assigned. A card that has gone marks the deployment `failed` with the missing index and the surviving inventory named — one card off the bus and a driver that stopped enumerating altogether are different problems with different next steps, and "GPU 2 is gone" alone does not distinguish them
  - **the same absence from the offer, the opposite fact.** A card `node.toml` excludes is also missing from `Present`, and reporting that as hardware failure would send an operator to `dmesg` for a line they wrote themselves. `Build` now takes the measured inventory *and* the narrowed offer, which is the only way to tell a decision from a fault
  - a caller that measured nothing — `agent plan` against a hand-written document — is **not** read as having measured no GPUs. That distinction is the whole difference between a preview and an alarm on every deployment on the node
  - **the node is flagged by derivation, not by a column.** The offer is what the node declared and `gpus` is what it measured on its last heartbeat, so the two disagreeing *is* the fact; `nodary node show` reports it. A stored flag would be one more thing to clear, and the clearing is what gets forgotten. A node that has never reported an inventory has not lost a card, so it is not flagged
  - the failure carries its reason onto the wire unconditionally: `0006_fleet.sql` pairs `failed` with a non-null `last_error` in a CHECK, so a failure reported bare does not merely lose the reason — it fails the whole heartbeat transaction and takes every other deployment's state on that node with it
  - **never rebooted**, and that is asserted rather than merely intended. A "never" cannot be tested by exercising it — no input makes it happen, which is the claim — so a test asserts the only thing that can be: nothing in `internal/agent` can reach `reboot`, `shutdown`, `poweroff` or `halt`. The tempting fix for a wedged GPU is a reboot, and the cost of one here is a machine that comes back to a passphrase prompt at a console in a locked rack ([03 §7](../specs/03-agent.md#reboot-safety))

## Egress isolation

The mechanism matters more than the intent here: the obvious approach —
`IPAddressDeny=any` on the model unit — filters `nerdctl` rather than the model,
looks correct, reviews clean, and enforces nothing.
· [03 §5](../specs/03-agent.md#5-egress-isolation)

- [x] **R4-26** Create the `nodary-isolated` CNI bridge network at install: host-local address, **no default route**, IP forwarding disabled, nftables dropping forwarded traffic from its subnet
  - *done:* **a published port is listening after the network exists**, asserted alongside the isolation. The isolation half passes in a configuration that is silently broken: docker's `--internal` network gives no default route and discards `-p 127.0.0.1:…` without a warning, leaving a deployment that is `active`, holds its GPU, passes a health probe and passes `verify-egress` while being unreachable by the gateway. The mechanism [03 §5](../specs/03-agent.md#5-egress-isolation) specifies — an ordinary bridge with the default route removed inside the namespace — gives both. CNI will have its own version of the trap; this assertion is what catches it · [spike §5](../spike-fips-and-manifest.md#--internal-silently-breaks-ingress--this-is-the-finding)
  - **it did, and the assertion caught it.** The configuration carried `isGateway: false`, so the bridge held no address and the host had no route into the subnet: portmap installed its DNAT and every published port pointed somewhere undeliverable. Ingress is now `isGateway: true` with `isDefaultGateway: false` and no listed route — the host can reach in, the container cannot reach out. The unit test asserted `isGateway: false` on the reasoning that it "would give the container a default route", which it does not, and that wrong assertion is what held the bug in place

- [x] **R4-29** `nodary node verify-egress` runs a probe inside a live deployment's namespace, asserting that a route off-box, a DNS lookup and a connection to a known-external address all fail
  - *done:* it runs after every deployment start and on demand; a failure marks the deployment non-compliant and raises a critical alert. Removing it from its route is the control plane's half, like health — a route is fleet state, and R3 owns it
  - **the three checks are not redundant, and that was measured.** In a container with its default route removed, TCP to an external address was refused and a DNS lookup *resolved, with live answers*: docker injects a resolver at `127.0.0.11` on the container's own loopback, which needs no route and proxies out.   - **verified as root against a live container**, which nothing else in the repo could do: inside the namespace, no default route, `example.com` unresolvable and `1.1.1.1:443` unreachable — while a request to the published port on `127.0.0.1` was answered · [`scripts/verify-privileged.sh`](../../scripts/verify-privileged.sh) step 12

A control whose answer is always "could not tell" is one people learn to skip. It now retries while inconclusive and stops once it has a verdict, so a converged deployment is not re-probed every fifteen seconds
  - a **host control run** accompanies every verdict. Every check passes by failing, so on a host with no egress the in-namespace probe would report compliant without establishing anything; that case reports `inconclusive`, which is the honest answer and is what an air-gapped site would otherwise silently get
  - **the probe was IPv4-only while the enforcement was not.** R4-39 made the bridge refuse IPv6 precisely because a container can autoconfigure a global address and a default route from a router advertisement — and the route check read `/proc/net/route`, which is IPv4, so exactly that namespace reported "no default route".   - both families, folded into the **existing two checks** rather than added as new ones.   - **the unreachable default is measured, not assumed.** A host with no IPv6 egress carries two `::/0` entries on `lo`, flags `00200200` and metric `ffffffff` — RTF_REJECT with an infinite metric, the kernel's spelling of `unreachable default`.   - *done:* **the verdict leaves the node.** It was logged on the machine that reached it and went no further, so the control plane — the one place an assessor or an operator looks — knew nothing about the control the whole boundary rests on.   - *done:* the download itself runs in a goroutine independent of the reconcile loop (`Build()` runs roughly once a minute and remembers nothing between calls, wrong for something that can take hours), polled through `Status`, which never blocks past a map lookup — `agent plan` never constructs a `Downloader` at all, so a one-shot preview can never be what starts one
  - *deferred, and said so rather than silently missing:* one `HF_TOKEN` per node, not per model or per repository. File-granularity resume (skip or refetch a whole file), not a mid-file `Range` request
