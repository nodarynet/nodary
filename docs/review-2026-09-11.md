# Review — nodary as a CUI-boundary tool

**Reviewer:** external, evaluating adoption · **Date:** 2026-09-11 · **Tree:** `cc77239`, v0.0.1-rc1

Read as a senior engineer at a ten-to-forty person R&D supplier that handles CUI, is subject to
CMMC Level 2, and is deciding whether to run this. Not a security audit and not an assessment:
an adoption review, written for the people who would have to operate it and for whoever writes
the SSP afterwards.

Method: read the specifications and the tracker, then the code, then ran the binary against a
scratch database to check that what the code appeared to do is what it does. Findings marked
*reproduced* or *measured* were executed. The rest are read from source and cross-checked
against [`docs/tasks/`](tasks/).

---

## 1. Verdict

**The architecture is right for a site this size. The build is not ready to carry a control
anybody would name in an SSP.**

The engineering is unusually good for a fifteen-day-old tree: three direct dependencies, a
static binary, a clean race-detector run, and design documentation better than most funded
products ship. The shape — explicit placement, one SQLite file, agent-initiated outbound only,
no Kubernetes — is exactly the shape a four-to-eight GPU-box site wants, and the argument in
[ADR 0001](adr/0001-no-orchestrator.md) holds up.

The problem is that the record-keeping layer is substantially ahead of the enforcement layer,
and the README does not distinguish them. Several capabilities the front page presents as
enforced are objects the system stores, displays, diffs and exports — and never acts on. For a
general-purpose tool that is an ordinary roadmap gap. For a tool whose whole proposition is
*"describe something you can show"*, it is the specific failure mode that matters, because it
hands an SSP author language for controls that are not in force.

Worth stating plainly, because it changes what the fix is: the project already keeps an honest
gap list in [`plans/mvp.md` §6](plans/mvp.md). That list is incomplete against what is below,
but it exists. This is a marketing failure rather than an engineering one, and the correction
is to promote the honest list into the buyer-facing documents, not to write one.

**Recommendation:** pilot on non-CUI workload. Do not cite it in the SSP. Re-evaluate when
[R3](tasks/R3-gateway.md) and [R5](tasks/R5-install.md) close.

---

## 2. What is genuinely good

Not a codebase to be dismissive about. These are above what we normally get from a vendor at
this stage.

- **The audit chain works as advertised.** Rewriting a justification directly in SQLite made
  `audit verify` name the break at the correct sequence number and exit non-zero. *(reproduced)*
  The read path also refuses a `detail_json` column that is merely *decodable* rather than
  canonical, which closes a real hole — a trailing second JSON document would otherwise decode
  to the same map and re-hash clean.
- **The CUI boundary is structural, not procedural.** The usage schema is closed, so there is
  no free-text field to write a prompt into; a test fails the build if a path from a request
  body to storage appears; and LiteLLM's six logging settings are written explicitly and then
  re-asserted against the rendered file rather than trusted ([ADR 0006](adr/0006-cui-boundary-and-fips.md)).
- **The crypto is considered rather than cargo-culted.** PBKDF2-SHA256 at 600k iterations with
  self-describing parameters; per-message HKDF subkeys under a 192-bit salt specifically to
  escape the NIST SP 800-38D random-nonce GCM call budget; a CSR that contributes a public key
  and nothing else, with the subject built server-side.
- **The egress reasoning is better than most security teams'.** Measuring that a container with
  its default route removed still resolves DNS through an injected in-namespace resolver, and
  then building both the CNI configuration and the probe around that fact, is the kind of thing
  that usually gets found in an incident instead. The probe also runs a host control and
  reports `inconclusive` rather than `compliant` when the host itself reaches nothing.
- **Unimplemented verbs fail loudly.** `backup`, `upgrade` and `uninstall` each name the release
  and what it implements. No silent no-ops.
- **The documentation is exceptional** — 14 numbered specs, 8 ADRs, and plans carrying actual
  measurements rather than assertions.

## 3. Claimed versus enforced

Each row is a capability the README presents as shipped. "Stored only" was established by
grepping for enforcement sites outside the package that defines the setting.

Across the whole policy object, **11 of 16 profile settings have no enforcement site outside
`internal/policy`.** Some govern features that do not exist yet — derived images, custom
backends — and are honest placeholders. The rest govern features that do.

## 4. Findings

### 4.1 Blockers

**Every node falls off the fleet 90 days after enrollment** · R4-05 · `internal/api/pki.go:203`

Agent client certificates are issued with a 90-day lifetime and there is no renewal path
anywhere in the tree. Ninety days after install, every agent's certificate expires at roughly
the same time and the control plane loses the whole fleet at once. Running deployments keep
serving because nothing kills them, so the failure is quiet: what is lost is visibility and
control, not inference. Recovery is manual re-enrollment of every node with a fresh join token.
[11 §1](specs/11-failure-modes.md) already lists this row as owned by R4-05, which is open.

**One user can consume the entire fleet** · R3-08/09/10 · `internal/gateway/`

Limits are a first-class configured object: `nodary limits set --subject …` writes them,
`config export` carries them, the policy diff reasons about whether a change loosens them. The
gateway never reads them. No token bucket, no concurrency cap, no daily budget, no `429` path.
At this headcount that is not a theoretical fairness problem — one researcher's overnight batch
starves everyone else's interactive work and nothing in the product notices or says so.

**A `regulated` install mints credentials its own policy forbids** · `internal/cli/token.go` · *reproduced*

`policy show` reports `token_max_ttl_days 365`. The mint path consults policy for exactly one
thing — whether unattended tokens are allowed — and never checks the lifetime ceiling.

```console
$ nodary policy show | grep token_max
  token_max_ttl_days       365

$ nodary token create --user alice --kind sk --expires 3650d --justify "…" --yes
  sk for alice, id tok_hxavq7wwvfsiqeon, expires 2036-09-09T05:09:08.817Z.

$ nodary token create --user alice --kind sk --expires never --justify "…" --yes
  sk for alice, id tok_xgfeownkmnfkpfv4, expires -.
```

This is §3 in its most concrete form. An assessor reading the policy object and an operator
reading the token table are looking at two different systems.

**No backup, no upgrade, no uninstall** · R2-37, R5-15, R5-17

All three verbs are present and all three are stubs. The stated recovery story is that the
database is a single file — but the tooling that captures it alongside `secret.key`, without
which the database is unreadable, does not exist. [08 §4](specs/08-data-model.md) says
`nodary backup create` captures both by default and refuses a world-readable destination; that
sentence describes nothing that runs. Neither does a patch path: LiteLLM v1.98.0 is pinned by
digest, which is right, and moving off it when the next CVE lands currently means a manual
reinstall.

### 4.2 High

**The LiteLLM master key is visible in `ps`** · `internal/install/units.go:139`

The gateway unit passes the credential as a command-line argument, so it lands in the process's
`argv` and is readable by any local account through `/proc/<pid>/cmdline`. That key is the
single credential LiteLLM accepts and grants its full administrative API. The
`EnvironmentFile=` is already loaded into the unit — the fix is to read the variable inside the
process instead of interpolating it into `ExecStart=`.

**Unauthenticated login attempts serialize the whole control plane** · `internal/api/routes.go:95` · *measured*

Two problems compound.

There is no lockout, no throttle and no delay on failed authentication anywhere in the tree.
That is [NIST SP 800-171](https://csrc.nist.gov/pubs/sp/800/171/r2/upd1/final) 3.1.8
unaddressed, on the one endpoint reachable before any credential exists.

And password verification is deliberately routed through the audit mutation seam — correctly,
since the rehash-on-stale write belongs in the same transaction as the login it authorized —
which means the 600k-iteration PBKDF2 runs *inside* the single SQLite write transaction. One
hash measured at 68 ms on this hardware, and `internal/store` caps the writer pool at one
connection by design. Roughly fifteen login attempts per second is therefore enough to hold the
write lock continuously, blocking audit records, agent status posts and usage rows behind an
attacker who has not authenticated. Each failure also appends an audit row, and with no
retention task that growth is unbounded.

**There is no remote administration, so every administrator needs root on the control plane** ·
[10 §2](specs/10-cli.md) · `internal/cli/fleet.go:32`

`--server URL` is specified as a global flag and is not implemented; the source says so. Every
`nodary` verb operates on the local SQLite file. The HTTP API that would substitute is partial
— no usage endpoint (R2-32), no model registration (R2-28), no node revoke (R2-26), no
pagination (R2-21), no `If-Match` (R2-22), no idempotency (R2-23) — and there is no client
for it.

The consequence matters more than the gap. A CLI invocation with no credentials file resolves
to a local-root principal with full admin authority, and the audit record reads
`actor: root, method: local`. Presenting a personal token changes the attribution string but
not the authority, and `internal/cli/session.go` says exactly that. So on a team where several
people administer, the choice is broad root SSH on the box holding the audit chain, or waiting
for the API. Either way, attributing privileged actions to individuals — the thing this product
exists to provide — is currently the hardest part of it to achieve.

**The audit chain has no anchor outside the box it protects** · R2-41 · `internal/audit/sink.go`

[07 §3](specs/07-identity-audit.md) is honest about this: *"A compromised control plane can
rewrite the whole chain consistently."* Shipping the JSONL mirror off-box is what converts
detection into something an attacker cannot quietly undo — and the network sink that would do
it is not built. The available sinks are a local file, stdout and stderr, configured through an
environment variable rather than `server.toml`.

The signed evidence bundle does not close this. Its Ed25519 signing key is generated on the
install and sealed under `secret.key` on the same host, so root on the control plane can
rewrite the chain and re-sign a consistent bundle. The signature establishes integrity since
export, not integrity since the event. That is a real and useful property; it is not the one
*"verifiable without trusting us"* implies to a reader who has not read [13](specs/13-evidence.md).

*Available today:* point a log shipper at `/var/log/nodary/audit.jsonl` into WORM storage.
Records carry `seq` and `hash`, so a receiver dedupes and detects gaps without trusting the
sender, and `audit verify --mirror` validates the copy on a machine that has never seen the
database. This works — it just has to be the customer's integration rather than a feature.

### 4.3 Medium

**Suspending a user does not end their session** · `internal/api/auth.go:61`

The session store caches the resolved principal — user, role and all — and `lookup` returns it
without re-reading state. Bearer tokens are re-resolved on every request and revoke
immediately; sessions do not. Under `default` the session TTL is 10080 minutes, so a suspended
account or a downgraded role stays live for up to a week. Sessions are also in-process only, so
a control-plane restart logs everyone out.

**The gateway holds a read-write handle to the audit database** · `internal/cli/gateway.go:56`

The gateway is the largest attack surface in the product: the only component that ever touches
a prompt and the only one facing arbitrary user input. It opens the same SQLite file the audit
chain lives in, for writing, because it records usage rows and stamps `last_used_at`. A gateway
compromise is therefore a compromise of the tamper-evident log. Splitting metering into its own
database, or putting the usage write behind an append-only interface, would cost little.

**The spec says the master key is encrypted at rest; it is not** · [08 §4](specs/08-data-model.md) · `internal/cli/server.go:730`

Spec 08 §4 and the `internal/secret` package doc both state that the LiteLLM master key is
sealed under `secret.key`. It is written in cleartext to `/etc/nodary/gateway.env` and again
into `/etc/nodary/litellm.yaml`, both mode 0640. The TOTP seeds and the agent CA key *are*
sealed as documented — only this one is not. In a product sold on the accuracy of its own
documentation, a security spec that overstates the implementation costs more than its severity
suggests.

**Egress isolation covers IPv4 only** · `internal/agent/network.go:184`

The nftables rule is `ip saddr 10.88.0.0/24 drop` — v4 only. There is no `ip6` counterpart and
no `disable_ipv6` on the `nodary0` bridge. On a dual-stack host where router advertisements
reach the bridge, a container could acquire a global v6 address and a route the rule does not
cover. The probe would catch it through the DNS check but not the connect check, which targets
`1.1.1.1:443`. Cheap to close.

**Egress verification is structurally inconclusive at an air-gapped site** · `internal/agent/egress.go:198`

Every check establishes isolation by failing, so the probe runs a host control to distinguish
"isolated" from "this host reaches nothing anyway". The logic is correct and the honesty is
admirable. The consequence is that on a genuinely air-gapped host — the stated target customer
— the verdict is always `inconclusive` and never `compliant`. The flagship isolation evidence
is unavailable precisely where it matters most, and it is worth deciding whether a different
control (an interface-level assertion, say) should carry that evidence instead.

Also worth knowing before this runs on a monitored segment: the host control resolves
`example.com` and dials `1.1.1.1:443` from the control plane on every verification. On a CUI
network that is an outbound connection to a third party that egress alerting will flag.

**Usage records cannot be attributed to a node or a GPU** · `internal/gateway/proxy.go:85`

The `Usage` struct carries `DeploymentID` and `NodeName`. The gateway populates neither — it
fills user, token, route, model and request id and leaves the rest NULL. Per-node and per-GPU
chargeback, which is most of what a site this size wants metering for, is not available from
the data as recorded. `GET /usage` (R2-32) is also unimplemented, so the numbers are reachable
only from the CLI on the box.

**Login distinguishes a suspended account from an unknown one** · `internal/identity/password.go:149`

The comment two lines above says the login path must not reveal which. It does: a suspended
user returns `ErrNotActive` and an account with no password returns `ErrNoPassword`, while an
unknown username returns `ErrBadPassword`. Username enumeration, minor alone, compounding with
the absent lockout above.

**Country-code origin filtering is a control with no verifiable input** · `internal/policy/profiles/regulated.toml`

Setting aside that it is unenforced today, the design deserves a question. The `regulated`
profile carries `model_origin_allowlist = ["US","FR","GB","CA","DE"]` and
`model_origin_denylist = ["CN"]`. The origin is whatever the registering operator declares at
`model register`; nothing derives or verifies it. A model's declared country of incorporation
also does not describe its risk — the same weights mirrored under a US organization are
declared US.

As an *attestation* — a recorded, attributable statement that somebody asserted a provenance —
this is defensible and genuinely useful, and it is consistent with how the rest of the product
treats operator claims. As an *enforced control* it would be checkbox assurance. The product
should say which of the two it is before it reaches an SSP narrative.

## 5. What to fix

Ordered by what blocks what.

### Before a pilot — days

1. **Move the master key off the command line.** One line in `internal/cli/gateway.go` to fall
   back to `os.Getenv("NODARY_MASTER_KEY")`, and drop the flag from the unit template.
2. **Add the IPv6 drop rule and `disable_ipv6` on `nodary0`.** Two more entries in the existing
   `ensureDropRule` loop and one sysctl beside the v4 one.
3. **Ship `audit.jsonl` into WORM storage** with a log shipper, and verify the copy with
   `audit verify --mirror` on a separate host. This is what makes the chain's tamper-evidence
   mean anything before R2-41 exists.
4. **Correct the README.** Strike OIDC, the SIEM sink and the FIPS build from the editions
   table; qualify "enforces per-user rate and budget limits". The honest list in
   [`plans/mvp.md` §6](plans/mvp.md) already exists and is missing these rows — extend it and
   promote it. How a vendor responds to this is the cheapest available signal about whether
   they are a safe dependency.

### Before production — weeks

5. **Certificate renewal (R4-05).** Renew at two-thirds of lifetime over the existing mTLS
   channel. Until it lands, the 90-day cliff is a scheduled outage that has to be diarized.
6. **Rate limiting and quota in the gateway (R3-08/09/10).** Token bucket on `rpm`, `tpm`,
   `daily_tokens` and `max_concurrent`; a `429` naming which limit was hit. The configured
   objects already exist — this is wiring, not design.
7. **Login throttling and lockout.** Addresses 3.1.8 and removes the write-lock denial of
   service in one change. Move password verification out of the write transaction, or
   rate-limit ahead of it.
8. **`backup create` / `restore` (R2-37),** capturing `secret.key` with the database and
   refusing a world-readable destination, as [08 §4](specs/08-data-model.md) already specifies.
9. **Re-check session principals against user state,** or shorten the `default` TTL from a week
   to something that bounds the revocation window.
10. **Upgrade path (R5-15),** required for CVE response on the LiteLLM dependency.

### Before it appears in an SSP — months

11. **Close the policy object's enforcement gaps** — retention pruning, token TTL ceiling,
    origin checks — *or* have `policy show` mark unenforced fields as declarative. Either is
    acceptable. Displaying them as though they are in force is not.
12. **Node guardrail enforcement (R4-14/15/16),** so [00 §5](specs/00-overview.md)'s
    trust-boundary table is true.
13. **A remote administration path** — `--server` in the CLI, or the remaining API surface with
    a client — so administrators are not root on the control plane and privileged actions
    attribute to people rather than to `root`/`local`.
14. **Separate the gateway's database handle** from the audit chain's.
15. **Network audit sink (R2-41),** retiring the shipper stood up in step 3.

---

## 6. Decision

A good project caught at an awkward moment. The parts that are built are built carefully, and
the front page describes the finished product rather than this build.

The risk is not that nodary is insecure. It is that an SSP author reads `policy show`, writes
down four controls, and two of them are display-only — which is a worse position than having no
tool, because it converts an acknowledged gap into an unknowing misstatement.

So: pilot on non-CUI research workload, where the architecture's real strengths pay off
immediately and nothing depends on the unenforced half. Ship the four day-scale fixes.
Re-evaluate at R3 and R5 close, and treat the README correction as the gate on further
investment.
